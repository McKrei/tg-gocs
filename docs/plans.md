# Комплексный план оптимизации и рефакторинга Family Docs Agent Bot

Этот план объединяет улучшение быстродействия (пользовательский опыт) и реструктуризацию архитектуры (удобство расширения, отказоустойчивость). План разделен на 5 логических блоков с фиксированным порядком выполнения.

## Порядок выполнения

Блоки выполняются строго последовательно — каждый следующий опирается на результаты предыдущего:

| Очередь | Блок | Обоснование |
|---------|------|-------------|
| 1 | Блок 5: CI/CD | Все последующие изменения будут защищены автотестами при деплое |
| 2 | Блок 1: Быстродействие | Немедленный эффект для пользователя, минимальные структурные изменения |
| 3 | Блок 4: Отказоустойчивость | Стабильность инфраструктуры до масштабной реструктуризации |
| 4 | Блок 2: Модульная архитектура | Массовый рефакторинг импортов — безопасен только при наличии CI/CD и тестов |
| 5 | Блок 3: Реестр инструментов | Зависит от модульной структуры из Блока 2 |

## Блок 5: Контроль качества в CI/CD (Безопасность деплоя)

> Выполняется первым — защищает все последующие изменения.

**Контекст:** В данный момент деплой происходит при каждом push в `main` без единой проверки. Если в коде есть критическая синтаксическая ошибка или не пройдены тесты, сломанная версия все равно попадет на сервер и бот перестанет отвечать.

### Что делаем:
1. **Разделение шагов в GitHub Actions:** Переписываем workflow `.github/workflows/deploy.yml`.
   - Вводим две последовательные задачи (jobs): `lint_and_test` и `deploy`.
   - Задача `deploy` запускается только при успешном завершении `lint_and_test` (`needs: lint_and_test`).
2. **Запуск проверок:** В задаче `lint_and_test` настраиваем окружение Python, устанавливаем зависимости через `uv sync` и запускаем проверку форматирования (`ruff check`), типов (`mypy`) и быстрых тестов (`make test`).
3. **Health Check после деплоя:** После `make up` в SSH-скрипте добавляем проверку жизнеспособности контейнера:
   ```bash
   sleep 10
   CONTAINER_STATUS=$(docker ps --filter name=tg-gocs --format '{{.Status}}')
   if echo "$CONTAINER_STATUS" | grep -q "Up"; then
     echo "✅ Контейнер запущен: $CONTAINER_STATUS"
   else
     echo "❌ Контейнер не запустился!"
     docker logs tg-gocs --tail 50
     exit 1
   fi
   ```
   Если контейнер не поднялся — job завершается с ошибкой, пользователь получает Telegram-уведомление о неудачном деплое.

### Изменения в документации:
- Добавить информацию о структуре проверок в [`docs/cicd.md`](cicd.md).

### Тестирование:
- Тестирование самого workflow при коммитах в ветку, отличную от `main`.

### Влияние на функциональность:
- Гарантия того, что в рабочее окружение (production) никогда не попадет неработоспособный код бота.

### Как проверить при запуске:
- Намеренно закоммитить в ветку ошибку типизации (например, передать строку вместо числа) и убедиться, что GitHub Actions остановил процесс на этапе тестирования, не запуская деплой на сервере.

## Блок 1: Оптимизация критических путей (Быстродействие)

**Контекст:** Пользователь испытывает задержки (до 15–20 секунд) при анализе документов (ожидание черновика) и при подтверждении сохранения. Нам необходимо ускорить транзакции без изменения функционала.

### Что делаем:
1. **Параллельное сохранение:** В `callbacks.py` переписываем шаги сохранения. Загрузку файла в Google Drive (`save_to_local_and_drive`) и получение векторного эмбеддинга от LLM (`get_embedding`) запускаем параллельно с помощью `asyncio.gather()`. Сейчас в `_persist_document` эмбеддинг запрашивается последовательно после сохранения — это ~2с впустую.
2. **Параллельный сбор метаданных при анализе:** Выносим вызов `get_existing_structure()` из тела функции `classify_document()` в `agent.py`. В `handle_start_analysis` (callbacks.py) запускаем сбор структуры (`get_existing_structure()`) параллельно с подготовкой/склеиванием PDF через `asyncio.gather()`. Готовый `structure_info` передаём в `classify_document` как параметр.
3. **Облегченный поиск дубликатов:** Модифицируем `find_similar_document` в `tools.py`.
   - Если расстояние схожести векторов < 0.10 (почти 100% совпадение) — считаем документ дубликатом автоматически, **без** вызова `check_is_duplicate()`.
   - Если расстояние в диапазоне 0.10 – 0.20 — помечаем документ как «возможный дубликат» и предлагаем пользователю выбор в интерфейсе, минуя повторный запрос к LLM.
   - Если расстояние > 0.20 — считаем документ уникальным.
4. **Прогресс-сообщения для пользователя:** Вместо одного статичного «⏳ Объединяю файлы и анализирую...» отправляем промежуточные обновления через `edit_text`:
   - `🔍 Анализирую документ...` (перед вызовом classify_document)
   - `📂 Определяю категорию и проверяю дубликаты...` (после classify, перед find_similar)
   - Итого: финальный черновик. Пользователь видит, что бот работает, а не завис.

### Изменения в файлах:
- `src/agent/agent.py` — параметр `structure_info` в сигнатуре `classify_document()`.
- `src/bot/handlers/callbacks.py` — `asyncio.gather()` для параллельных операций, прогресс-сообщения.
- `src/agent/tools.py` — трёхуровневая логика в `find_similar_document()`.

### Изменения в документации:
- Обновить схемы взаимодействия (Flows) в [`docs/architecture.md`](architecture.md), зафиксировав параллельное выполнение шагов.

### Тестирование:
- Юнит-тест с использованием Mock для проверки времени выполнения: симулируем сетевую задержку Drive (5с) и LLM (2с), проверяем, что общее время выполнения `gather` составляет ~5 секунд (а не 7с).
- Тест граничных значений расстояния сходства векторов в `find_similar_document` для проверки правильности присвоения статусов дубликатов.

### Влияние на функциональность:
- Среднее время ожидания пользователя сократится на **40-60%** (минус 5–8 секунд на операциях).
- Пользователь видит промежуточные статусы — нет ощущения «зависания».

### Как проверить при запуске:
- Включить отладочные логи с фиксацией миллисекунд для старта и окончания сетевых операций в `callbacks.py`.

## Блок 4: Отказоустойчивость и кэширование (Стабильность инфраструктуры)

**Контекст:** Сетевые запросы к Google Drive API медленные и могут завершаться ошибками. При сохранении бот делает запросы поиска папок по всей глубине пути (например, проверить `Медицина`, затем проверить `Жена`). Если Drive недоступен, бот ломается.

### Что делаем:
1. **Кэширование путей папок:** Внедряем in-memory кэш сопоставления локальных путей категорий и ID папок Google Drive (например, `Медицина/Жена` -> `1aBcDe...`). Кэш храним в оперативной памяти с TTL 24 часа. Реализация: класс `FolderCache` в `src/drive/cache.py` на базе `dict` + `time.monotonic()` для TTL. Кэш инвалидируется при создании новой папки.
2. **Graceful Degradation при сбое Drive с отложенной синхронизацией:** Если при сохранении файла Google Drive API возвращает ошибку (таймаут, лимит квот), бот:
   - Сохраняет файл в локальное хранилище.
   - Делает запись в БД с отметкой `gdrive_link = NULL`.
   - Создает запись в таблице `pending_uploads` для отложенной синхронизации.
   - Выводит пользователю сообщение: «Документ сохранен локально. Синхронизация с Google Drive произойдет позже».
3. **Таблица отложенных задач:** Новая SQLAlchemy-модель:
   ```python
   class PendingUpload(Base):
       id: Mapped[uuid.UUID]
       local_path: Mapped[str]       # путь к локальному файлу
       target_path: Mapped[str]      # целевой путь в Drive
       document_id: Mapped[uuid.UUID | None]  # связь с documents
       created_at: Mapped[datetime]
       attempts: Mapped[int] = 0
       last_error: Mapped[str | None]
       status: Mapped[str] = "pending"  # pending | completed | failed
   ```
   При старте бота и каждые 15 минут — фоновая задача (`asyncio.create_task`) проходит по `pending_uploads` со статусом `pending`, пытается загрузить файлы, обновляет `documents.gdrive_link` при успехе.
4. **Предварительное сжатие фото:** Перед отправкой изображения в ИИ-агент на анализ, сжимаем его с помощью библиотеки Pillow (до разрешения максимум 1600x1200, качество JPEG 80%). Реализация: функция `compress_image()` в `src/utils/image.py`, вызывается в `files.py` сразу после скачивания файла.

### Изменения в файлах:
- `src/drive/cache.py` — новый файл, класс `FolderCache`.
- `src/drive/uploader.py` — интеграция кэша в `_find_or_create_folder_sync()`.
- `src/db/models.py` — модель `PendingUpload`.
- `src/db/repository.py` — CRUD-методы для `pending_uploads`.
- `src/services/retry_uploads.py` — новый файл, фоновая задача ретраев.
- `src/bot/main.py` — запуск фоновой задачи при старте.
- `src/utils/image.py` — новый файл, `compress_image()`.
- `src/bot/handlers/files.py` — вызов `compress_image()` после скачивания.

### Изменения в документации:
- Обновить разделы «Надёжность» и «Хранение данных» в [`docs/architecture.md`](architecture.md).

### Тестирование:
- Юнит-тест кэша: проверить TTL-инвалидацию и инвалидацию при создании папки.
- Юнит-тест с Mock: перевести Google Drive клиент в режим `HttpError 503`, проверить, что бот сохраняет файл локально, создает запись в `pending_uploads` и корректно записывает в `documents`.
- Юнит-тест `compress_image`: проверить выходные размеры и качество.

### Влияние на функциональность:
- Бот становится полностью работоспособным даже при временном отсутствии связи с Google Drive.
- Время выгрузки сокращается за счет кэширования путей (минус 1-3 API-запроса на операцию).
- Время передачи и анализа изображений сокращается за счет сжатия.

### Как проверить при запуске:
- Искусственно ограничить доступ к доменам Google в `.env` (указать неверный ID корневой папки или неверный путь к credentials) и проверить успешность сохранения документа локально.
- Восстановить доступ и дождаться автоматической синхронизации из `pending_uploads`.

## Блок 2: Модульная архитектура и изоляция доменов (Поддержка и Расширяемость)

**Контекст:** Текущая кодовая база сгруппирована технически (все хэндлеры в `bot/handlers/`, все инструменты в `agent/tools.py`). При добавлении новых областей (например, Календарь, Задачи, Финансы) придется менять общие файлы, что приведет к росту зацепления кода и багам.

### Что делаем:
1. **Выделение ядра (Core):** Создаем директорию `src/core/`, куда переносим общесистемный код:
   - `src/core/config.py` — конфигурация (из `src/config.py`)
   - `src/core/db/engine.py` — подключение к БД (из `src/db/engine.py`)
   - `src/core/llm/client.py` — клиент LLM (из `src/llm/client.py`)
   - `src/core/llm/embeddings.py` — эмбеддинги (из `src/llm/embeddings.py`)
   - `src/core/utils/` — логирование, retry-декоратор, утилиты изображений (из `src/utils/`)
   - `src/core/drive/` — клиент Drive, uploader, кэш (из `src/drive/`)
2. **Доменная реструктуризация:** Создаем директорию `src/modules/` для прикладных модулей.
3. **Создание модуля Documents:** Переносим всю логику работы с документами в `src/modules/documents/`. Внутри модуля создаем изолированные:
   - `handlers/` (бывшие хэндлеры файлов, поиска, инбокса, калбэков)
   - `models.py` (SQLAlchemy-модель таблицы `documents` + `pending_uploads`)
   - `tools.py` (инструменты для агента, относящиеся к документам)
   - `states.py` (FSM состояния документов)
   - `agent.py` (оркестратор агента для документов)
   - `services/` (sync, retry_uploads)
4. **Бот как тонкая оболочка:** `src/bot/main.py` остается точкой входа, но становится минимальным: создает `Bot`, `Dispatcher`, импортирует и подключает роутеры из модулей, запускает фоновые задачи.
5. **Миграция импортов:** Создаем временные реэкспорты (`src/config.py` → `from src.core.config import *`) на переходный период, затем удаляем. Все тесты обновляем под новые пути.

## Блок 3: Динамический реестр инструментов и модульный FSM (Интеграция Агента)

**Контекст:** Сейчас ИИ-агент получает жестко прописанный список инструментов из `agent/tools.py` (100+ строк ручного JSON-описания). При добавлении новых модулей (например, календаря с инструментом `create_event`) нам нужно автоматически подключать их к ИИ-агенту, не переписывая ядро оркестратора.

### Что делаем:
1. **Реестр инструментов (Tool Registry):** В `src/core/agent/` создаем класс `ToolRegistry` и декоратор `@register_tool`. Декоратор автоматически генерирует JSON-схему из type hints и docstring функции. Пример использования:
   ```python
   @register_tool(
       name="search_documents",
       description="Поиск документов по текстовому запросу",
       mode="classify",  # "classify" = read-only, "full" = все операции
   )
   async def vector_search(query: str, limit: int = 5) -> list[dict]:
       ...
   ```
   Это заменяет ручной `TOOLS_MAP`, `TOOLS_SCHEMA`, `CLASSIFY_TOOLS_MAP` и `CLASSIFY_TOOLS_SCHEMA` — единственный источник правды для инструментов.
2. **Динамический сбор из модулей:** При старте бота `ToolRegistry` сканирует `src/modules/*/tools.py`, импортирует файлы и собирает все декорированные функции. Для каждого модуля при импорте `tools.py` декораторы автоматически регистрируют инструменты в глобальном реестре.
3. **Модульная регистрация хэндлеров и FSM:** Каждый модуль экспортирует функцию `register_module()` в своем `__init__.py`, которая возвращает:
   - `Router` (с подключенными хэндлерами и FSM-состояниями)
   - Список фоновых задач (`Callable`) для запуска при старте
   В `main.py` при старте: импорт всех `src/modules/*/`, вызов `register_module()`, подключение роутеров к `Dispatcher`, запуск фоновых задач.
4. **Логирование при старте:** При запуске бота выводим в логи:
   - Список зарегистрированных модулей
   - Список зарегистрированных инструментов с их режимами (classify/full)
   - Список подключенных роутеров

### Изменения в файлах:
- `src/core/agent/registry.py` — новый файл, `ToolRegistry`, `@register_tool`.
- `src/core/agent/orchestrator.py` — базовый оркестратор (рефакторинг из `agent.py`), использует `ToolRegistry` вместо хардкода.
- `src/modules/documents/tools.py` — замена `TOOLS_MAP` / `TOOLS_SCHEMA` на декораторы.
- `src/modules/documents/__init__.py` — функция `register_module()`.
- `src/bot/main.py` — автосканирование и подключение модулей.

### Изменения в документации:
- Добавить в [`docs/architecture.md`](architecture.md) схему работы динамического реестра.
- В [`AGENTS.md`](../AGENTS.md) прописать правила именования и регистрации инструментов через декораторы.

### Тестирование:
- Юнит-тест реестра инструментов: создаем тестовую функцию с декоратором `@register_tool`, проверяем, что она успешно регистрируется, а её JSON-схема генерируется корректно из type hints.
- Юнит-тест автосканирования: создаем мок-модуль в temp, проверяем, что он обнаруживается и подключается.

### Влияние на функциональность:
- Любой добавленный модуль (Календарь, Задачи, Финансы) сможет мгновенно наделить ИИ-агента новыми способностями без ручной настройки ядра бота.
- Устраняется рассинхронизация между `TOOLS_MAP` и `TOOLS_SCHEMA` — единственный источник правды.

### Как проверить при запуске:
- При запуске бота в логах должен появиться список зарегистрированных модулей и инструментов.
- Весь базовый цикл документов должен работать идентично прежнему.
